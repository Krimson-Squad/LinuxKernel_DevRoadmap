# Lesson 10.7: Developing Device Drivers in Rust (extended)

## Overview

This lesson goes deeper than 10.3: patterns for binding Rust drivers to existing C APIs, the FFI traps to avoid, and how to structure a driver that is genuinely safer than its C twin.

## Patterns for Rust device drivers

1. **Wrapper types for MMIO** — `IORemapped` owns the mapping and gives you checked `readl`/`writel`. Never expose raw addresses.
2. **`Operations` trait for fops** — implement type-safe `read`/`write`/`ioctl`; the kernel calls through a generated C `file_operations`.
3. **Guard-protected state** — `Arc<Mutex<State>>` or a single `struct` guard; the driver object owns everything.
4. **Error translation** — return `Result<_, kernel::error::Error>`; conversion to kernel errno happens in the glue.

## The FFI traps

- **Ownership handoffs**: a C callback that takes ownership must be wrapped in a type that can't be dropped twice.
- **`&mut` vs raw pointers**: interior mutability under `Arc` — use `Mutex` or `RefCell` variants, never hand out `&mut` behind `Arc`.
- **Callbacks re-entrancy**: mark IRQ-safe and be careful re-locking in callbacks.
- **String/NUL issues**: kernel strings are `CStr`/`CString`, not `str`; NUL-termination is the abstraction layer's job.

## A minimal char driver skeleton

```rust
impl kernel::file_operations::FileOperations for MyFile {
    kernel::declare_file_operations!(read, ioctl);

    fn read(
        _this: &<Self as FileOperations>::Data,
        data: &mut kernel::io_buffer::IoBufferWriter,
        _offset: u64,
    ) -> Result<usize> {
        data.write_slice(b"hello\\n")
    }
}
```

The kernel glue wires `fops.read` through a C `ssize_t (*read)(struct file*, ...)` trampoline with the borrow checking already applied.

## Testing strategy for Rust drivers

- **KUnit**: pure logic compiled as `#[cfg(test)]`; kernel-side runtime via `kunit`.
- **QEMU**: target a `virtio` or platform device in the emulator for integration tests.
- **Userspace harness**: open the char device from a test binary; drive reads/writes/ioctls and assert results.

## Suggested exercise

Sketch `MyFile` above, register it with a `device_register!` and a platform `probe`, and note the three places where the compiler protected you from a C footgun (owned resources, lock ordering, or pointer lifetime).
