# Lesson 10.8: Submitting Rust-Based Patches (extended)

## Overview

Submission for Rust kernel code mirrors the C flow but demands extra care: pinned toolchains, `unsafe` reviews, and reproducible builds. This lesson makes the checklist concrete.

## Before you format

1. **Base**: work from `linux-next` (that's what maintainers accept).
2. **Build clean**: `make LLVM=1 W=1` (add `-Werror` courtesy) — zero warnings.
3. **Test**: load your module/driver, unload, plus the exercised path (read/write/ioctl).
4. **Checkpatch**: `./scripts/checkpatch.pl --strict your.patch` → clean.

## Preparing the series

```bash
git format-patch -N --cover-letter --subject-prefix="PATCH v1" out/
./scripts/get_maintainer.pl out/patch*
```

Cover letter states:

- Toolchain versions used (`rustc x.y.z-nightly`, `clang/LLVM` a.b).
- What the patch does and why (in one paragraph).
- How it was tested (the exact commands).

## Sign-off and tags

```text
Signed-off-by: You <you@example.com>
```

Body may add `Link:`, `Fixes:` (if fixing a Rust commit, format `Rust: <commit>` is expected).

## The review loop specifics

- Reply inline to each comment; resend as `[PATCH vN]`.
- For `unsafe`: maintainers will ask "why is this safe?" — preempt with a comment on every `unsafe` block.
- Toolchain bumps: if you raised the pinned version, justify it and show the failing old version.

## Reproducible tests — the gold standard

```text
[root]: make LLVM=1 defconfig && scripts/config -e RUST
[root]: make LLVM=1 -j8
[root]: insmod rust_minimal.ko && rmmod rust_minimal.ko
[root]: dmesg | grep rust
Tested-by: You <you@example.com>
```

## Exercise

Take the sample doc change from 10.4 but now as a full series: run `git format-patch -1 --cover-letter`, paste `checkpatch` output, and write the cover letter body (toolchain, what, why, test commands) as if you were mailing it to rust-for-linux right now.
