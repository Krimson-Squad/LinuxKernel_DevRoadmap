# Lesson 9.1: Kernel Debugging Techniques

## Overview

Debugging the kernel is debugging where you can't just set a breakpoint in a debugger GUI. The good news: Linux ships an enormous set of inspection tools. This lesson maps them to the questions they answer.

## Kernel logs: `dmesg`

The first stop for any kernel problem:

```bash
dmesg | tail -100
dmesg -l err,warn
journalctl -k -p err         # with systemd, filter by level
```

Kernel messages come from `printk()` and are rate-limited per level (`KERN_ERR`, `KERN_WARN`...). Add your own `pr_info()`/`pr_err()` in driver code to trace your logic.

## Debugger: GDB / KGDB / KDB

- **GDB** against a `vmlinux` lets you inspect static structures and symbols from a crash dump or kdump.
- **KGDB** — full live breakpoints in the kernel over a serial/VM connection (`kgdboc=ttyS0`).
- **KDB** — built-in shell for memory inspection and backtraces without a remote debugger.

```bash
gdb vmlinux
(gdb) disassemble do_sys_open
(gdb) p task_current(current)
```

## Tracing: `ftrace` and `perf`

- **ftrace** — trace any function call in the kernel:

```bash
echo do_sys_open > /sys/kernel/tracing/set_ftrace_filter
echo function > /sys/kernel/tracing/current_tracer
cat /sys/kernel/tracing/trace
```

- **perf** — profiling, events, and call graphs (`perf top`, `perf record -g`, `perf trace` drops in as a lightweight `strace`).

- **systemtap / eBPF tools** — `bpftrace` gives scriptable one-liners for kernel behavior without recompiling.

## `panic`, `oops` and kdump

An oops prints the register dump and call trace; `panic_on_oops` turns it into a full panic. Enable `CONFIG_KALLSYMS` + kdump so `/proc/kcore` gives you a post-mortem.

## Exercise

Write a deliberate error into a module you control, reload it, and use `dmesg -w` to see the trace live. Then run `perf top` for a minute and `bpftrace -e 'tracepoint:syscalls:sys_enter_openat { @[comm] = count(); }'` to see which tools surface real kernel activity.
