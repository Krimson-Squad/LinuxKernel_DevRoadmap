# Lesson 11.2: Reviewing and Testing Patches

## Overview

Seniority in kernel development is earned by reviewing, not writing. A good review catches bugs early, saves maintainer time, and teaches the reviewer as much as the author.

## Patch review checklist

1. **Context**: what is the patch trying to fix? Does the commit message explain why?
2. **Style**: `checkpatch.pl` clean? Naming, line lengths, K&R braces.
3. **Correctness**: boundary conditions, error paths, resource cleanup (`goto` patterns), locking discipline.
4. **Impact**: does it break other architectures (`ARCH`, endianness, 32-bit)?
5. **Fit**: is the fix appropriate, or does a bigger redesign exist upstream?

## How to give feedback that lands

- **Inline, not top-posted**: quote the code line, comment right under it.
- **Suggest, don't rewrite**: `s/foo/bar/` micro-edits + one-liner "because...".
- **Separate nits from must-fix**: "could be" vs "must be".
- **Test it**: pull their branch, build `W=1`, load their module, run the reproducer.
- **Sign your endorsement**: `Reviewed-by:` (after careful read) or `Tested-by:` (only after you ran the test).

## Testing others' patches

```bash
b4 am <message-id>             # fetch a mailing-list series, apply it cleanly
make LLVM=1 -j8 && make W=1     # build + warnings
sudo insmod <their module>.ko   # exercise the changed path
# run the reproducer from the series cover letter
```

Then reply: tree you used, config, commands, result.

## Quality gates to enforce

- `W=1` warnings = reject-by-default (unless justified).
- A `Fixes:` or `Link:` reference missing for a fix = request the tag.
- Missing test description in the message body = ask for the exact reproducer.

## When to escalate

If a patch looks wrong but you're unsure: reply with "I'm not confident about X; maintainers?" — pushing a wrong "NACK" hurts you.
