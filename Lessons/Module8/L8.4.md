# Lesson 8.4: Submitting Your First Patch

## Overview

A kernel patch is a specific Git commit, formatted as an email-ready diff, with a strict message and a sign-off. This lesson is the end-to-end flow from your working tree to a maintainer's inbox.

## 1. Keep the commit small and correct

- One logically-single change per commit.
- Build it (**`make W=1`** clean before submitting).
- Tested on `linux-next` at minimum.

## 2. Write the commit message

Subject line: `<area>: <short summary>`, all under ~60-70 chars, imperative mood.

Body: explain *why*. Reference the bug (`Fixes: <commit hash>`, or a Link). Credit reviewers with `Reported-by`, `Reviewed-by`, `Tested-by` tags.

```
net: fix null deref in xfrm state release

xfrm_state is freed before the timer callback runs, causing a NULL
deref when the XFRM_MSG_DELSA handler fires on a stale state.

Fix the ordering by cancelling the timer before freeing the state.

Fixes: 4b6e5e7e (xfrm: release state on delete)
Signed-off-by: Alice Dev <alice@example.com>
```

## 3. Create the patch series

```bash
git format-patch -1 --cover-letter -o out/   # 1 commit, with cover later
git send-email $(ls out/*.patch)             # or feed git send-email directly
```

The last line of every commit **must** be `Signed-off-by: You <you@example.com>` — it certifies you wrote/rightfully took the code.

## 4. Address the right audience

```bash
./scripts/get_maintainer.pl patchfile.patch
```

Mail to the listed maintainers + subsystem list with `Cc:` on lists. Keep only the diff, the cover letter, and per-patch notes — no attachments.

## 5. The review loop

- Expect feedback: style, API, test requests.
- Reply inline to review comments; resend a *new* version `[PATCH v2]` when changes land.
- Never force-push or top-post in review threads.
