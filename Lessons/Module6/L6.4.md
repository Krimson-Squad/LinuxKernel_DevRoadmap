# Lesson 6.4: Linux I/O Systems

## Overview

I/O is how the kernel talks to the outside world: block devices like NVMe/SATA, character devices like serial ports, and the thousands of drivers behind them. All of it funnels through a small set of common abstractions.

## Two device families

- **Block devices** transfer data in fixed-size blocks (sectors) and support random access: disks, SSDs, loop devices. Represented by `struct block_device`, requested via `request_queue`.
- **Character devices** transfer byte streams one at a time: ttys, keyboards, mice, serial ports. Represented by `struct cdev` and `file_operations`.

`block/` and `drivers/` hold the implementations; the common core abstractions live in `block/` for I/O and `kernel/`/`drivers/base/` for the device model.

## The I/O path (block example)

1. A process writes to a file → VFS → filesystem code (`fs/ext4/` for ext4).
2. The filesystem submits a `struct bio`.
3. The block layer (`block/blk-mq.c`) stacks the request and schedules it to a hardware queue via a multi-queue (`blk-mq`) driver.
4. The driver (`drivers/nvme/host/`) programs the controller, and the completion interrupt reports the result back.

```text
user write -> syscall -> VFS -> fs/ext4 -> bio -> block layer -> nvme driver -> hardware
                                         ^------------- blk-mq ------------^
```

## Watching I/O happen

```bash
iostat -x 1        # per-device utilization
cat /sys/block/nvme0n1/queue/scheduler   # I/O scheduler (mq-deadline / none)
blktrace -d /dev/nvme0n1 & stracer ...   # trace requests
```

## Suggested exercise

Run a write-heavy workload (`dd if=/dev/zero of=/tmp/f bs=1M count=200`) while watching `iostat -x`. Then search the kernel source for `blk_mq_submit_bio()` in `block/blk-mq.c` and identify where the request is handed to the driver.
