# Lesson 9.3: Writing Device Drivers

## Overview

A driver makes hardware look like normal kernel objects: a char driver looks like a file in `/dev`, a net driver looks like a network device. Everything user space touches is a `file_operations` table underneath.

## Driver structure

Every driver has four pillars:

1. **`probe`** — called when the bus finds matching hardware: allocate resources, map registers, register the device.
2. **`remove`** — undo everything `probe` did.
3. **`file_operations`** (char/block) or device callbacks — the actual I/O API.
4. **`id_table`** — which hardware this driver claims (PCI/USB/platform IDs).

```c
static const struct file_operations my_fops = {
	.owner   = THIS_MODULE,
	.open    = my_open,
	.read    = my_read,
	.write   = my_write,
	.release = my_release,
};
```

## Device nodes and user space

Char drivers register with a major/minor number:

```bash
mknod /dev/mydrv c 240 0     # manual node for major 240, minor 0
```

Modern systems auto-create nodes via udev from the device model. User space does `open("/dev/mydrv")` → kernel calls `my_open()`.

## Exposing registers to user space

```c
#define MY_BASE 0x6000     /* pretend I/O region */
static char __iomem *regs;

regs = ioremap(MY_BASE, 0x100);       /* map hardware memory */
ret  = readb(regs + 0x10);            /* read a register byte */
iounmap(regs);
```

`ioremap`/`readb` translate hardware addresses into kernel virtual addresses safely.

## Testing drivers

- **KUnit** — kernel-native unit tests compile against the driver code.
- **Emulation**: QEMU can emulate PCI, USB, and platform devices — run your driver against fake hardware.
- **Fault injection**: `fault-injection/` (`fail_make_request`) forces error paths to exercise cleanup code.
- **A userspace test harness** that opens the node and does read/write through `file_operations`.
