# Lesson 8.3: Coding Style and Conventions

## Overview

The kernel has one style rulebook: `Documentation/process/coding-style.rst`. It was born from long tradition and is applied so strictly there's a checker script. This lesson teaches what matters and how to verify before you post.

## The fundamentals

- **Indentation**: tabs, 8 columns wide. No spaces for indentation, ever.
- **Line length**: aim under 80 columns; occasional runs into the 80s are tolerated, not encouraged.
- **Brackets**: K&R style — opening brace on the same line for functions *only* differs in `if`/`for`/`while` (same line), function blocks (own line).
- **Spacing**: single spaces around binary operators; no space before `(` after function names (`if (x)` yes, `foo (x)` no).
- **Naming**: `snake_case`, short but meaningful; no camelCase, no Hungarian notation.
- **Comments**: explain *why*, not what; C style `/* */` is standard.

## A styled example

```c
static int example_init(struct platform_device *pdev)
{
	struct device *dev = &pdev->dev;
	int ret;

	if (!dev->of_node)
		return -ENODEV;

	ret = reset_control_get(dev);
	if (ret)
		return ret;

	dev_info(dev, "probed\n");
	return 0;
}
```

## Common mistakes to avoid

- Functions over a screen long — split them.
- `goto` only for error cleanup paths, jumping forward, one per label.
- Massive `if` chains over a `switch`.
- Magic numbers without a named constant or `#define`.

## Checking your work

The kernel ships lint scripts:

```bash
./scripts/checkpatch.pl --strict --no-tree changes.patch
```

And a build-time compiler warnings pass:

```bash
make W=1 2>&1 | less
```

Fix every warning before posting; maintainers will check.

## Exercise

Write a small function in worst-case style (camelCase, braces on wrong lines, 100-column lines), then run `scripts/checkpatch.pl` on a generated patch and fix each error it reports. Repeat until zero issues.
