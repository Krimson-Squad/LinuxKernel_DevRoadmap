# Lesson 10.2: Writing Kernel Modules in Rust

## Overview

Rust kernel modules follow the same shape as C ones — init/exit, attribute-backed metadata — but with a safety-first structure and a different build dance.

## Module anatomy (Rust)

```rust
use kernel::prelude::*;

module! {
    type: HelloModule,
    name: "hello_rust",
    author: "You",
    description: "A first Rust kernel module",
    license: "GPL",
}

struct HelloModule;

impl kernel::Module for HelloModule {
    fn init(_name: &'static CStr, module: &'static ThisModule) -> Result<Self> {
        pr_info!("hello from Rust!\n");
        Ok(Self)
    }
}
```

- The `module!` macro generates the C-facing `module_init`/`module_exit` and metadata sections.
- All kernel-facing code goes through `kernel::` abstractions — no raw pointers unless wrapped.

## Building

Kernel Rust support requires `clang` + `bindgen` + a **nightly** rustc (the kernel pins a toolchain version), plus `CONFIG_RUST` and `CONFIG_RUST_BUILD_ASSERT`:

```bash
make LLVM=1 rustavailable
make LLVM=1 defconfig
scripts/config -e RUST
make LLVM=1 -j$(nproc)
```

In-tree modules live under `samples/rust/` (e.g. `rust_minimal`, `rust_print`) and build with `CONFIG_SAMPLES` + `CONFIG_SAMPLE_RUST_MINIMAL`.

## Interop with C

- C can call into Rust via flattened symbols (`extern` "C" and `#[no_mangle]` when unavoidable, but the abstractions try to keep it clean).
- Rust consumes kernel C APIs through the **safe wrappers** in `rust/kernel/`; the unsafe layer sits in `bindings` generated by `bindgen`.
- The golden rule: raw kernel API lives behind `unsafe`; modules should only touch the safe abstractions.

## Constraints and pitfalls

- `no_std`: no `std` types — use `core::`, `kernel::` types, `Vec`/`String` from `kernel::alloc``.
- Global state must be `static`/`const`; use kernel locks (`kernel::sync::Mutex<...>`) not `std`.
- Panics abort (UB in a module); prefer `Result` and `kernel::error::to_result`.

## Suggested exercise

Enable `CONFIG_RUST` and build `samples/rust/rust_minimal`, then `insmod` and confirm the init message via `dmesg`. Modify the `pr_info!` string and rebuild to feel the iteration loop.
