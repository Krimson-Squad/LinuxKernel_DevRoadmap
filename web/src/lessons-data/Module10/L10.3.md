# Lesson 10.3: Developing Device Drivers in Rust

## Overview

Drivers are where Rust's safety pays off most: they touch memory, locks, and callbacks — exactly the code where C drivers leak bugs. A Rust driver builds the same `file_operations`/`platform` structures, but through type-safe abstractions.

## Structure of a Rust driver

```rust
use kernel::{
    prelude::*,
    platform,
};

struct MyDriver {
    regs: ioremap::IORemappedPinned,
    lock: Mutex<MyState>,
}

impl platform::Driver for MyDriver {
    type Data = ();

    fn probe(dev: &platform::Device, data: &mut Self::Data) -> Result<Self> {
        let regs = dev.iomap_resources_regions()?;      // safe ioremap
        Ok(Self { regs, lock: Mutex::new(Default::default()) })
    }
}

kernel::platform::driver_register!(MyDriver, id_table, platform::driver::Register);
```

Notice: no raw `readl`/`writel` calls exposed to the driver author — `IORemapped` wraps them in checked methods, and state goes behind a real mutex instead of ad-hoc atomics.

## Differences from C drivers

| Aspect | C driver | Rust driver |
|---|---|---|
| Registers | `ioremap` + `readl` | checked `IORemapped` wrapper |
| State | global + locks by discipline | owned fields, guards by type system |
| Callbacks | filled `file_operations` | trait objects implementing `Operations` |
| Errors | `-EINVAL` literals | typed `Result<E: ToErrno>` |

## Memory and concurrency at the driver level

- The borrow checker enforces a single writer for state — races that C finds only under load are rejected at compile time.
- `Arc`/`Mutex`/`spinlock` wrappers map 1:1 to kernel primitives but give you guard lifetimes.
- Buffer management reuses `Box`/`Vec` from `kernel::alloc` — the driver never frees manually.

## Testing

- Same techniques as C: KUnit for logic, QEMU for device emulation, and the userspace read/write harness.
- Add Rust-specific unit tests (`#[cfg(test)]`) inside `cargo`-capable crates for pure logic.
