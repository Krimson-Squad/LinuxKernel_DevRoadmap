# Lesson 10.5: Rust in the Linux Project: Overview (extended)

## Overview

Where Lesson 10.1 introduced the idea, this lesson sends you into the source tree to see where Rust actually lives, what works today, and where the boundaries are.

## Status in upstream

- Merged starting **Linux 6.1** (initial infrastructure + examples).
- Each release since lands new safe abstractions in `rust/kernel/` and occasionally a new sample/module.
- Rust is **not** required: `CONFIG_RUST` is off by default; C remains the baseline.

## Where Rust is allowed in the tree

| Area | State |
|---|---|
| `rust/kernel/` | Safe abstraction layer — actively maintained |
| `samples/rust/` | Example modules — `rust_minimal`, `rust_print`, `rnull` |
| `drivers/rust/` | Where new Rust drivers attach (currently a skeleton + working examples) |
| `Documentation/rust/` | Docs: quick-start, general information, do's-and-don'ts |
| Core subsystems | Reviewed case-by-case; no wholesale rewrites |

## Tooling

- **`bindgen`** generates `rust/bindings/bindings_generated.rs` from kernel headers.
- **`cargo`** is *not* the build driver; `kbuild` invokes `cargo rustc`/`cargo build` under the hood via the `rust/` Makefile targets.
- **`clang`/`LLVM`** required: `make LLVM=1`; a pinned nightly rustc for the `fortify` and `alloc` bits.
- **`rust-analyzer`** is the recommended IDE LSP; `make LLVM=1 vmlinux` creates `rust-project.json`.

## Limitations today

- No `std`; no dynamic `Arc::clone` on `no_alloc` kernels unless configured.
- The safe API surface is smaller than C's — expect to wait for or contribute new wrappers.
- `unsafe` is still needed at abstraction boundaries and for some hardware patterns; the goal is minimizing it, not eliminating it.

## Suggested exercise

Run `make LLVM=1 rustavailable` to validate toolchain. Then open `rust/kernel/lib.rs` and list the five subsystems (types) the abstraction layer currently exports (modules/devices/fs/net/sync/...).
