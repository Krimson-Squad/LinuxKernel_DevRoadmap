# Lesson 6.1: Architecture of the Linux Kernel

## Overview

The Linux kernel is a modular monolith: one big chunk of code that boots into supervisor mode, organized so its parts stay decoupled. Understanding the layers helps you find where any feature lives.

## The layered view

1. **System call layer** — the user-visible ABI. Syscall handlers live under `kernel/`, `fs/`, `mm/`, `net/`, `ipc/`. The dispatch table is in `arch/<arch>/entry/syscalls/`.
2. **Core kernel** — process and task management, scheduling, signaling, locking, timekeeping (`kernel/`, `sched/`).
3. **Subsystems** — memory management (`mm/`), VFS (`fs/`), networking (`net/`), block and character I/O, device model (`drivers/base/`).
4. **Drivers** — the `drivers/` tree, organized by bus (PCI, USB, ...) and type (net, gpu, tty, ...).

## How components communicate

- **Functions and headers**: most internal APIs are plain C calls declared in `include/linux/`.
- **Hooks/callbacks**: subsystems expose operations structures (file operations, net device ops, bus drivers) that lower layers fill in.
- **Kernel threads and work**: deferred work via `workqueue`, kernel threads, and interrupts glue asynchronous pieces together.
- **Public interfaces**: `EXPORT_SYMBOL` marks functions linkable from other modules.

## A practical map

```text
syscall table  ->  fs/read_write.c  ->  vfs_read()
                                    ->  file->f_op->read_iter
                                    ->  fs/ext4/file.c  (ext4-specific)
```

That one path is the whole architecture in miniature: user ABI → core VFS → subsystem → driver.

## Suggested exercise

Pick a subsystem (say memory). Open `mm/` and list its top files (`mmap.c`, `page_alloc.c`, `slub.c`, `ksm.c`), then read `mm/mmap.c`'s `do_mmap()` to see how responsibilities drop between the VFS layer and the memory subsystem.
