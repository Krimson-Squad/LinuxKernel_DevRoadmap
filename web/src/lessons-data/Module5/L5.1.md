## Overview

System programming is the discipline of writing software that interacts directly with the operating system kernel. Where application programming sits on top of libraries and frameworks, system programming reaches through the system call interface to manage files, processes, memory, and inter-process communication.

## Why it matters

Everything you do in a shell — copying files, piping output, killing processes — is convenience wrappers around system calls. Kernel developers must think at this layer because the kernel *is* the layer the calls land on.

## What system programming covers

- **File manipulation**: opening, reading, writing, and closing files via file descriptors.
- **Process control**: creating, waiting on, and terminating child processes.
- **Inter-process communication**: signals, pipes, shared memory, and sockets.
- **Memory management**: allocating and mapping memory from user space.
- **Networking**: creating sockets and talking to remote hosts.

## User space vs kernel space

Your program runs in **user space**. Whenever it needs a privileged operation — creating a process, touching hardware, allocating big memory — it makes a **system call** that traps into **kernel space**, where the kernel performs the operation on your behalf and returns a result.

## A first example

```c
#include <stdio.h>
#include <unistd.h>

int main(void) {
    /* write() is a system call: fd 1 is stdout */
    write(1, "hello, kernel\n", 14);
    return 0;
}
```

Compile with `gcc hello.c -o hello` and run it. `write()` never touches your hardware — it hands the bytes to the kernel, which writes them to the terminal device.

## Exercise

Compile the example above, then run it under `strace ./hello` (install `strace` if needed). `strace` prints every system call the program makes — look for `write` and the process setup calls that came before it.
